# Как агенту добавить результат в атлас

Агент добавляет текст, ссылки на данные и описание визуализации. Сайт сам создаёт страницу, запись атласа и карточку исследования. Обычному материалу не нужны React, CSS и ручное редактирование навигации.

Сначала прочитайте корневой `AGENTS.md`, актуальное состояние исследования и `docs/WRITING_GUIDE.md`. Успешный запуск программы ещё не доказывает содержательную правильность результата.

## Карты в первую очередь

Пользователь предпочитает рассматривать результаты на картах. Для каждого пространственного результата — о населённых пунктах, территориях, услугах и связях — добавляйте содержательную карту или тематический слой и включайте переход к нему в материал. Не ограничивайтесь текстом и сложным графиком, если расположение объектов объясняет вывод лучше.

- Покажите прежде всего **где и что происходит**: распределение, изменения, различия территорий, доступность или модельные связи. Название карты формулируйте как понятный вопрос или вывод.
- Добавляйте столько карт, сколько нужно для разных выводов: например, общий рисунок, различия регионов и подробный пример. Жёсткой нормы количества нет. Несколько простых карт предпочтительнее одной перегруженной; одинаковые карты с разными заголовками не нужны.
- График дополняет карту, когда лучше объясняет динамику, сравнение величин или распределение значений. Не заменяйте полезную временную кривую бессмысленным набором карт. Для результата без пространственного смысла карта не обязательна.
- Если пригодных геоданных нет, укажите ограничение; не придумывайте координаты, контуры, зоны доступности или связи ради картинки. Пропуски, модельные оценки и наблюдения различайте явно.
- Переиспользуйте зарегистрированные слои и шаблоны `settlement-map` / `service-links`; новые данные подключайте по [готовой инструкции слоёв](LAYERS.md). Задавайте нужные слои через `mapState.layers` и добавляйте визуализацию в `visualIds` материала. Общая декоративная мини-карта страны не заменяет карту конкретного результата.
- Перед публикацией откройте материал и связанное состояние карты: проверьте соответствие показателя, территории и периода, легенду, единицу, источник и ограничения, читаемость подписей в обеих темах. Каждая карта должна помогать понять конкретный вывод.

## Подготовка

```bash
npm --prefix web install
python scripts/site_content.py --help
python scripts/site_content.py validate --json
```

Реестры лежат в `web/content`. Это обычные JSON, а `body` материала — строка Markdown. Команды CLI по умолчанию работают с текущим репозиторием; `--root` перед подкомандой позволяет проверить изолированную копию.

## Новый материал

Работайте в отдельной ветке. Стабильный ID используется в адресе; выбирайте смысловое имя, а не номер запуска.

```bash
python scripts/site_content.py new \
  --research population --kind method --id population-coverage-readout \
  --title 'Как читать покрытие базы населения' \
  --summary 'Покрытие населения и точность связывания — разные показатели.' \
  --topic 'Качество данных' --territory 'Россия' --period '2002–2021' \
  --evidence method \
  --source-url 'https://github.com/ZakBu/russian-settlements-research/blob/main/POPULATION_BASE.md'
```

Команда создаёт **черновик**, а не публикацию. Заполните `sourceCommit` полным коммитом фактического источника, закрепите ссылку источника на этот коммит, добавьте `body`, зарегистрированные `datasetIds` и `visualIds`. Первый абзац — вывод, далее доказательства, метод, ограничения. Для каждого численного вывода укажите единицу, год, источник, территорию и знаменатель доли.

Повтор идентичной команды не создаёт копию. Команда откажется заменить изменённый материал: дальнейшие правки вносятся явно в существующий JSON. Только после содержательной проверки меняйте `visibility` на `published`. Дата `updatedAt` меняется при изменении результата или объяснения, не при технической пересборке.

## Данные и визуализации

1. Найдите набор в `datasets.json`; если его нет, добавьте точную версию источника с ограничениями. Используйте существующий каталог научных выпусков и проверенные контрольные суммы. Не выбирайте GitHub Latest.
2. Получите компактный ряд из реальных таблиц расчёта. Исходная база населения остаётся неизменной. Тяжёлые Parquet, GeoJSON, карты и архивы хранятся в выпусках; генерируемые веб-данные исключены из Git.
3. Создайте описание по зарегистрированному шаблону. В файле значений допустимы только `categories`, `series`, `data`, `mapState`, `limitations`.

Новый независимый слой карты добавляется командой `site_content.py layer`, без изменения кода UI. Полный рабочий пример на реальном CSV с 197 центрами, точными полями и источником — в [инструкции слоёв](LAYERS.md).

Например, реальный ряд покрытия населения из `data/population_dataset.json` можно извлечь во временный JSON так:

```bash
python - <<'PY'
import json
from pathlib import Path
source = json.loads(Path('data/population_dataset.json').read_text())
rows = source['coverage']
Path('/tmp/population-coverage-values.json').write_text(json.dumps({
    'categories': [str(r['census_year']) for r in rows],
    'series': [{'name': 'Покрытие населения',
                'values': [r['coverage_percent'] for r in rows]}],
    'limitations': ['Покрытие населения не измеряет точность связывания НП.']
}, ensure_ascii=False))
PY
python scripts/site_content.py visual \
  --id population-coverage-chart --template census-trend \
  --dataset-ref REGISTERED-DATASET-ID \
  --title 'Покрытие населения в рабочем слое' --unit '%' \
  --caption 'Доля зачтённого населения по каждой переписи; не оценка точности связывания.' \
  --values-file /tmp/population-coverage-values.json
```

Замените `REGISTERED-DATASET-ID` существующим ID из реестра. CLI намеренно не подставляет случайные данные. `null` сохраняется как отсутствие наблюдения; значение `0` означает измеренный ноль. Не заменяйте пропуски нулями ради красивого графика.

Добавьте ID графика в материал. Его `datasetId` также должен входить в `datasetIds` материала. Палитру выбирайте по роли, не вводите свои HEX или ECharts options. Подробности — в [контракте](CONTENT.md) и [правилах дизайна](DESIGN.md).

## Просмотр, экспорт и PR

```bash
python scripts/site_content.py validate --json
python scripts/site_content.py preview --material population-coverage-readout
```

Предпросмотр запускает реальный Astro dev server. `--url-only` только печатает адрес. Производственная публикация не должна показывать черновики.

Для экспорта установите браузер один раз:

```bash
python -m pip install playwright
python -m playwright install chromium
python scripts/site_content.py export --visual population-coverage-chart \
  --format png --theme light --output /tmp/population-coverage.png
python scripts/site_content.py export --material population-coverage-readout \
  --format pdf --output /tmp/population-coverage.pdf
```

Экспорт открывает настоящую страницу визуализации или материала в Chromium с теми же ECharts-компонентами и шрифтами. Для существующего сервера добавьте `--url http://127.0.0.1:4321`. Вывод храните вне Git и публикуйте в отдельном выпуске при необходимости. Изменение фона страницы не заменяет проверку обеих тем.

```bash
python scripts/site_content.py submit \
  --title 'Добавить объяснение покрытия населения'
```

`submit` проверяет реестры, коммитит только изменения `web/content`, пушит текущую тематическую ветку и открывает PR через `gh`. Требуется настроенный доступ GitHub. С `main` команда требует `--branch content/population-coverage`. Другие заранее staged файлы блокируют команду. Удаление/изменение шаблонов интерфейса не является обычной публикацией контента и требует инженерного PR.

## Новое исследование, исправления и утренние обновления

- Для новой вкладки добавьте запись `research.json` с уникальным ID, названием, описанием, состоянием, содержательным итогом `summary`, следующим шагом `nextStep` и числом `order`. Привяжите материалы через `researchId`. Код навигации менять не нужно.
- Для исправления обновите объяснение, дату и научный статус. Отдельный материал `kind: correction` может указывать `supersedes`; старый материал сохраняет ID и получает `currency: superseded` либо `known-issues`.
- Для автоматических записей `state-*` сборка оставляет один текущий снимок состояния на исследование. Предыдущие автоматические снимки получают `visibility: archived` и `currency: superseded`, новый указывает `supersedes` на предыдущий. Старые даты, источники и текст сохраняются; прямые адреса остаются доступны. Авторские статьи этой операцией не меняются. Повтор сборки не переписывает уже согласованное состояние.
- Завершив исследование, обновите `research_context/current_state.json` по корневым правилам. Сборка запускает `python scripts/site_content.py sync-state --json`: для известных разделов `population_base` и `sgrt` она переносит явно записанные итоги в соответствующие исследования сайта и создаёт краткую запись со ссылками на точный коммит. Учитываются также изменения содержимого существующих документов `parts.*.results` и `parts.*.doc`, даже если короткий итог не изменился. Источник закрепляется на новейшем коммите состояния и этих документов; дата новой записи не предшествует этому коммиту. Одинаковое содержание имеет стабильный ID; изменение времени сборки не создаёт новость. Это детерминированное чтение состояния и описаний, а не AI-пересказ и не новая научная проверка.
- Для нового графика, полноценного объяснения, нового исследования или результата, не включённого в текущее состояние, агент регистрирует источник и материал командами выше. Новый ZIP сам по себе не объясняет свой научный смысл. Сборка не угадывает его содержание. Лента сообщает о результатах, исправлениях и отрицательных выводах, не о каждом rebuild.
- Публикационный координатор обновляет общий дневник и состояние исследования один раз за сеанс. Параллельные авторы работают в отдельных материалах, чтобы не конфликтовать в общих реестрах.
- Не объявляйте расписание научных агентов существующим, если настроена только сборка сайта. GitHub Pages размещает готовый сайт; исследования выполняются отдельно.
