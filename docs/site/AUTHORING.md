# Как агенту добавить результат в атлас

Агент добавляет текст, ссылки на данные и описание визуализации. Сайт сам создаёт страницу, запись атласа и карточку исследования. Обычному материалу не нужны React, CSS и ручное редактирование навигации.

Сначала прочитайте корневой `AGENTS.md`, актуальное состояние исследования и `docs/WRITING_GUIDE.md`. Структура и оформление документа описаны в [редакционном руководстве](EDITORIAL.md), адаптированном по Контур.Гайдам. Успешный запуск программы ещё не доказывает содержательную правильность результата.

## Как материал попадает в библиотеку

Публикуйте одну запись в `web/content/materials/ID.json`: общий каталог `/materials/` показывает её списком, карточкой и в связях. Выбирать между «Атласом» и «Знаниями» не нужно. `kind` описывает назначение страницы, `researchId` — исследование; карта может быть и у метода, и у результата.

Выберите 2–4 подходящих ID из [словаря тем](../../web/content/tags.json) и добавьте, например, `"tags": ["demography", "census", "data-quality"]`. Не пишите свободные варианты вроде «демография России» вместо существующего тега. Синонимы добавляются в `aliases` словаря, новая самостоятельная тема — отдельной записью с русским названием. Проверка `validate` отклоняет неизвестные ID и повторы. Поле необязательное для совместимости и автоматических снимков состояния; для авторской публикации темы выбираются явно.

Форматы карты/графика/таблицы определяются по содержимому. Для Markdown-иллюстрации дайте alt-текст о том, что нарисовано, например `Карта центров России по сочетанию динамики населения`; не пишите просто «рисунок». Это полезно читателю, поиску и фильтру формата. Не добавляйте фиктивную карту ради фильтра. Даты источников и научная территория остаются в своих полях; дата обновления не превращает модель в наблюдение.

Связывайте новый вывод с методом через `[[material-id|понятная подпись]]`. Если материал заменяет конкретную прежнюю публикацию, укажите существующий `supersedes`; тематическое сходство само по себе не доказывает исправление. Наборы данных регистрируются в `datasetIds`. Из этих явных связей строятся переходы и граф; агент не дорисовывает отношения по общему тегу.

## Карты в первую очередь

Пользователь предпочитает рассматривать результаты на картах. Для каждого пространственного результата — о населённых пунктах, территориях, услугах и связях — добавляйте содержательную карту или тематический слой и включайте переход к нему в материал. Не ограничивайтесь текстом и сложным графиком, если расположение объектов объясняет вывод лучше.

- Покажите прежде всего **где и что происходит**: распределение, изменения, различия территорий, доступность или модельные связи. Название карты формулируйте как понятный вопрос или вывод.
- Добавляйте столько карт, сколько нужно для разных выводов: например, общий рисунок, различия регионов и подробный пример. Жёсткой нормы количества нет. Несколько простых карт предпочтительнее одной перегруженной; одинаковые карты с разными заголовками не нужны.
- График дополняет карту, когда лучше объясняет динамику, сравнение величин или распределение значений. Не заменяйте полезную временную кривую бессмысленным набором карт. Для результата без пространственного смысла карта не обязательна.
- Если пригодных геоданных нет, укажите ограничение; не придумывайте координаты, контуры, зоны доступности или связи ради картинки. Пропуски, модельные оценки и наблюдения различайте явно.
- Переиспользуйте зарегистрированные слои и шаблоны `settlement-map` / `service-links`; новые данные подключайте по [готовой инструкции слоёв](LAYERS.md). Задавайте нужные слои через `mapState.layers` и добавляйте визуализацию в `visualIds` материала. Общая декоративная мини-карта страны не заменяет карту конкретного результата.
- Перед публикацией откройте материал и связанное состояние карты: проверьте соответствие показателя, территории и периода, легенду, единицу, источник и ограничения, читаемость подписей в обеих темах. Каждая карта должна помогать понять конкретный вывод.

## Подготовка

```bash
npm --prefix web install
python scripts/site_content.py --help
python scripts/site_content.py validate --json
```

Реестры лежат в `web/content`. Это обычные JSON, а `body` материала — строка Markdown. Команды CLI по умолчанию работают с текущим репозиторием; `--root` перед подкомандой позволяет проверить изолированную копию.

## Новый материал

Работайте в отдельной ветке. Стабильный ID используется в адресе; выбирайте смысловое имя, а не номер запуска.

```bash
python scripts/site_content.py new \
  --research population --kind method --id population-coverage-readout \
  --title 'Как читать покрытие базы населения' \
  --summary 'Покрытие населения и точность связывания — разные показатели.' \
  --topic 'Качество данных' --territory 'Россия' --period '2002–2021' \
  --evidence method \
  --source-url 'https://github.com/ZakBu/russian-settlements-research/blob/main/POPULATION_BASE.md'
```

Команда создаёт **черновик**, а не публикацию. Заполните `sourceCommit` полным коммитом фактического источника, закрепите ссылку источника на этот коммит, добавьте `body`, зарегистрированные `datasetIds` и `visualIds`. Первый абзац — вывод, далее доказательства, метод, ограничения. Для каждого численного вывода укажите единицу, год, источник, территорию и знаменатель доли.

Повтор идентичной команды не создаёт копию. Команда откажется заменить изменённый материал: дальнейшие правки вносятся явно в существующий JSON. Только после содержательной проверки меняйте `visibility` на `published`. Дата `updatedAt` меняется при изменении результата или объяснения, не при технической пересборке.

## Разметка документа

Поле `body` — обычный Markdown с небольшим набором согласованных блоков. Заголовки `##` и `###` автоматически формируют кликабельное оглавление и прямые ссылки на разделы. Не пишите оглавление вручную и не дублируйте `title` заголовком первого уровня в тексте. Повторяющиеся заголовки получают технические суффиксы, но читателю понятнее разные названия. На широком экране оглавление находится слева от колонки чтения, на узком — в раскрывающемся блоке над ней. Источники и связанные документы шаблон показывает под статьёй; отдельную боковую панель для них создавать не нужно.

| Возможность | Синтаксис | Что увидит читатель |
|---|---|---|
| Раздел | `## Как сравнивать переписи` | Заголовок, якорь и пункт оглавления |
| Подраздел | `### Пропуски значений` | Вложенный пункт оглавления |
| Ссылка на страницу вики | `[[population-coverage|Что означает покрытие базы]]` | Переход к существующему материалу |
| Ссылка на раздел | `[[map-reading-guide#территориальная-сетка|Территориальная сетка]]` | Переход сразу к нужному разделу |
| Внешний источник | `[Название источника](https://example.org/document)` | Обычная подписанная ссылка |
| Изображение | `![Осмысленное описание](https://example.org/figure.png "Краткое пояснение")` | Изображение с альтернативным описанием |
| Цитата | `> Точная цитата из источника` | Цитатный блок; автор и ссылка дописываются явно |
| Примечание | `> [!NOTE]` и строки `> Текст` | Блок «На заметку» |
| Совет | `> [!TIP]` и строки `> Текст` | Блок «Совет» |
| Важное пояснение | `> [!IMPORTANT]` и строки `> Текст` | Блок «Важно» |
| Ограничение | `> [!WARNING]` и строки `> Текст` | Блок «Ограничение» |
| Особое предупреждение | `> [!CAUTION]` и строки `> Текст` | Блок «Внимание» |
| Сноска | `Текст[^источник]` и определение `[^источник]: …` | Номер, примечание и обратная ссылка |
| Подробности | `:::details Заголовок` … `:::` | Нативный раскрывающийся блок |
| Зарегистрированная визуализация | `:::visual population-map` и закрывающая строка `:::` | Готовая карта или график в указанном месте |

Также работают маркированные и нумерованные списки, таблицы Markdown, **жирное выделение**, *курсив*, встроенный `код` и блоки кода с тройными обратными кавычками. Списки задач — запись состояния документа, а не форма сохранения данных читателя.

Внутренние ссылки используют стабильный ID существующего материала и читаемую подпись. Страница получает обратные ссылки из других документов автоматически. Для внешней научной ссылки выбирайте точный выпуск, коммит или датированный документ. Сноски служат комментариями; научные библиографические отсылки оформляйте как `[@source:1]`, `[@data:census-population]` или ссылку на запись реестра, например `[@HUFF1964]`. Получившийся номер `[N]` соответствует общему списку источников. Сноска не заменяет обязательные `sources`, `datasetIds`, `sourceCommit` и научные ограничения в метаданных материала.

Изображения добавляются стандартным Markdown: `![Что изображено](https://example.org/figure.png "Краткое пояснение")`. Допустимы HTTP/HTTPS и локальный путь от корня сайта; HTML для картинки не нужен. Для научной иллюстрации используйте точный URL версионированного выпуска, а не меняющийся Latest. Альтернативный текст описывает содержание, а не повторяет «картинка» или имя файла. Не передавайте значимый вывод только цветом.

Markdown-изображение получает номер рисунка и источник автоматически. URL сопоставляется с `sources` материала; если совпадения нет, сохраняется адрес самого изображения. Для научной иллюстрации дополнительно поясните показатель, единицу, период и ограничения рядом с изображением. Необязательный `title` — подсказка при наведении, он не заменяет эти сведения. Чужая иллюстрация не подписывается как построенная автором. Собственные карты и графики предпочтительно добавлять как зарегистрированные визуализации с набором данных. Крупные научные файлы остаются в версионированных выпусках.

У визуализации, вставленной через `:::visual`, ID входит в `visualIds` материала, а её набор — в `datasetIds`. Блок ставится отдельно между абзацами; вложение в таблицу, цитату или раскрывающиеся подробности не создаёт вторую интерактивную карту. Если визуализация уже вставлена в текст, не повторяйте её в начале статьи вручную. Для нового слоя сначала выполните [инструкцию слоёв](LAYERS.md).

Раскрывающийся блок начинается с `:::details` и заголовка на той же строке, заканчивается отдельной строкой `:::`. Его заголовок — простой текст. Не прячьте в нём вывод, критическое ограничение или единственную ссылку на источник. Для обычной статьи достаточно одного уровня подробностей. Заголовки внутри закрытых подробностей не добавляются в оглавление.

HTML, MDX, произвольные компоненты, CSS и JavaScript в материале не исполняются. Не вставляйте iframe или внешние скрипты. Новое поведение добавляется один раз в общий шаблон инженерным изменением; исследовательский агент выбирает уже доступный блок. Не используйте неизвестные ID как заглушки для публикации.

### Пример готовой структуры

Ниже — пример разметки объяснения карты с уже существующими материалами и визуализацией. Это образец структуры, а не новая публикация научного результата. Перед переносом в материал проверьте его тему и зарегистрированные ID; `population-map` использует набор `census-population`.

````markdown
## Как читать изменение населения

Цвет показывает направление изменения, а пропуск остаётся отдельным состоянием.
Сначала рассмотрите общий рисунок, затем приблизьте интересующую территорию.

:::visual population-map
:::

> [!WARNING]
> Наличие численностей разных лет само по себе не доказывает неизменность
> границ населённого пункта. Учитывайте сопоставимость записей.[^сопоставимость]

## Почему отсутствие сведений не равно нулю

Ноль означает измеренное значение. Пропуск означает, что нужного наблюдения нет.
Подробнее — [[population-coverage|как читать покрытие базы]].

| Состояние | Как интерпретировать |
|---|---|
| Есть значение | Наблюдение из указанного источника и года |
| Нет сведений | Наблюдение отсутствует; вывод о нуле делать нельзя |

:::details Как перейти к территории
Выберите режим населённых пунктов, районов или регионов на основной карте.
Найдите объект через поиск или нажмите на него. Сохраните ссылку на выбранное
состояние карты для коллеги.
:::

## Что проверить перед выводом

1. Уточните территорию и период показателя.
2. Прочитайте легенду и ограничения источника.
3. Сопоставьте карту с [[map-reading-guide|правилами чтения слоёв]].

[^сопоставимость]: [[population-comparability|Сопоставимость переписных данных]]:
    правила интерпретации изменений и границы применимости ряда.
````

Для цитаты сохраняйте точную формулировку, указывайте автора и ссылку. Если вы пересказываете источник, используйте обычный абзац и обозначайте пересказ. Лид и начало `body` не повторяют друг друга; редакционные правила и примеры выбора блоков — в [руководстве](EDITORIAL.md).

## Рисунки и ссылки по общему научному профилю

Правила нумерации, библиографии и печатного оформления собраны в [гайде научного оформления](GOST.md). Рисунки считаются сквозно внутри документа; таблицы имеют отдельный ряд. В сборном Word-документе счёт продолжается через границы материалов. Не вписывайте номера вручную.

- Для отсылки к рисунку используйте `[@fig:population-map]`; для первого Markdown-изображения — `[@fig:image-1]`.
- Библиографическая отсылка `[@source:1]` берёт первую запись `sources`, `[@data:census-population]` — зарегистрированный набор, `[@HUFF1964]` — научную публикацию из общего реестра. Это ссылки по идентификаторам, а не готовые номера `[1]`.
- Общий шаблон ставит название под рисунком и строку «Источник: построено автором по данным … [N]» для авторской визуализации зарегистрированных данных. Не дублируйте её в тексте. Для заимствованного изображения сохраняется настоящий источник, без присвоения авторства.
- Уточняйте библиографические поля по самому источнику. Не выдавайте дату сборки за дату обращения, а чтение аннотации — за прочитанную страницу статьи. Неполное описание остаётся неполным, даже когда номер и пунктуация расставлены автоматически.

## Данные и визуализации

1. Найдите набор в `datasets.json`; если его нет, добавьте точную версию источника с ограничениями. Используйте существующий каталог научных выпусков и проверенные контрольные суммы. Не выбирайте GitHub Latest.
2. Получите компактный ряд из реальных таблиц расчёта. Исходная база населения остаётся неизменной. Тяжёлые Parquet, GeoJSON, карты и архивы хранятся в выпусках; генерируемые веб-данные исключены из Git.
3. Создайте описание по зарегистрированному шаблону. В файле значений допустимы только `categories`, `series`, `data`, `mapState`, `limitations`.

Новый независимый слой карты добавляется командой `site_content.py layer`, без изменения кода UI. Полный рабочий пример на реальном CSV с 197 центрами, точными полями и источником — в [инструкции слоёв](LAYERS.md).

Например, реальный ряд покрытия населения из `data/population_dataset.json` можно извлечь во временный JSON так:

```bash
python - <<'PY'
import json
from pathlib import Path
source = json.loads(Path('data/population_dataset.json').read_text())
rows = source['coverage']
Path('/tmp/population-coverage-values.json').write_text(json.dumps({
    'categories': [str(r['census_year']) for r in rows],
    'series': [{'name': 'Покрытие населения',
                'values': [r['coverage_percent'] for r in rows]}],
    'limitations': ['Покрытие населения не измеряет точность связывания НП.']
}, ensure_ascii=False))
PY
python scripts/site_content.py visual \
  --id population-coverage-chart --template census-trend \
  --dataset-ref REGISTERED-DATASET-ID \
  --title 'Покрытие населения в рабочем слое' --unit '%' \
  --caption 'Доля зачтённого населения по каждой переписи; не оценка точности связывания.' \
  --values-file /tmp/population-coverage-values.json
```

Замените `REGISTERED-DATASET-ID` существующим ID из реестра. CLI намеренно не подставляет случайные данные. `null` сохраняется как отсутствие наблюдения; значение `0` означает измеренный ноль. Не заменяйте пропуски нулями ради красивого графика.

Добавьте ID графика в материал. Его `datasetId` также должен входить в `datasetIds` материала. Палитру выбирайте по роли, не вводите свои HEX или ECharts options. Подробности — в [контракте](CONTENT.md) и [правилах дизайна](DESIGN.md).

## Просмотр, экспорт и PR

```bash
python scripts/site_content.py validate --json
python scripts/site_content.py preview --material population-coverage-readout
```

Предпросмотр запускает реальный Astro dev server. `--url-only` только печатает адрес. Производственная публикация не должна показывать черновики.

Для экспорта установите браузер один раз:

```bash
python -m pip install playwright
python -m playwright install chromium
python scripts/site_content.py export --visual population-coverage-chart \
  --format png --theme light --output /tmp/population-coverage.png
python scripts/site_content.py export --material population-coverage-readout \
  --format pdf --output /tmp/population-coverage.pdf
```

Экспорт открывает настоящую страницу визуализации или материала в Chromium с теми же ECharts-компонентами и шрифтами. Для существующего сервера добавьте `--url http://127.0.0.1:4321`. Вывод храните вне Git и публикуйте в отдельном выпуске при необходимости. Изменение фона страницы не заменяет проверку обеих тем.

```bash
python scripts/site_content.py submit \
  --title 'Добавить объяснение покрытия населения'
```

`submit` проверяет реестры, коммитит только изменения `web/content`, пушит текущую тематическую ветку и открывает PR через `gh`. Требуется настроенный доступ GitHub. С `main` команда требует `--branch content/population-coverage`. Другие заранее staged файлы блокируют команду. Удаление/изменение шаблонов интерфейса не является обычной публикацией контента и требует инженерного PR.

## Word: отдельный материал и сборный документ

На опубликованной странице используйте «Скачать Word», на странице исследования — выгрузку исследования целиком. Файлы создаются при сборке из той же версии текста, рисунков и источников, что и сайт. Подготовленная иллюстрация статична; рядом остаётся ссылка на её интерактивную версию.

Для локальной выгрузки после `npm --prefix web run build`:

```bash
python scripts/site_content.py export --material map-reading-guide \
  --format docx --output /tmp/map-reading-guide.docx
python scripts/site_content.py export \
  --materials map-reading-guide,population-coverage \
  --format docx --output /tmp/selected-materials.docx
python scripts/site_content.py export --research sgrt \
  --format docx --output /tmp/sgrt.docx
```

Порядок ID в `--materials` задаёт порядок глав. Нумерация рисунков и библиография пересчитываются для всего сборного документа: повторный источник не превращается в новую запись только из-за границы главы. Собирайте общий файл этой командой, а не вставкой нескольких независимых `.docx` друг в друга.

Для профиля кафедры добавьте `--reference-doc /path/university.docx`. Печатный профиль по умолчанию и границы его применимости описаны в [GOST.md](GOST.md#печатный-профиль-word). Нужны установленные Pandoc и зависимости `requirements-site.txt`; сборка использует готовый конвертер, а не ручную вёрстку XML. Текст, заголовки, таблицы и ссылки остаются редактируемыми. При необходимости обновите поля оглавления и номеров страниц в Word.

После изменения текста или порядка рисунков в вики создавайте выгрузку заново. Проверяйте сам файл: совпадение отсылок и списка, подписи, длинные ссылки, переносы таблиц и отсутствие меню сайта на иллюстрации. Файл Word не подтверждает научную правильность материала. Крупные итоговые `.docx` хранятся в версионированных выпусках, не в истории Git.

## Новое исследование, исправления и утренние обновления

- Для новой вкладки добавьте запись `research.json` с уникальным ID, названием, описанием, состоянием, содержательным итогом `summary`, следующим шагом `nextStep` и числом `order`. Привяжите материалы через `researchId`. Код навигации менять не нужно.
- Для исправления обновите объяснение, дату и научный статус. Отдельный материал `kind: correction` может указывать `supersedes`; старый материал сохраняет ID и получает `currency: superseded` либо `known-issues`.
- Для автоматических записей `state-*` сборка оставляет один текущий снимок состояния на исследование. Предыдущие автоматические снимки получают `visibility: archived` и `currency: superseded`, новый указывает `supersedes` на предыдущий. Старые даты, источники и текст сохраняются; прямые адреса остаются доступны. Авторские статьи этой операцией не меняются. Повтор сборки не переписывает уже согласованное состояние.
- Завершив исследование, обновите `research_context/current_state.json` по корневым правилам. Сборка запускает `python scripts/site_content.py sync-state --json`: для известных разделов `population_base` и `sgrt` она переносит явно записанные итоги в соответствующие исследования сайта и создаёт краткую запись со ссылками на точный коммит. Учитываются также изменения содержимого существующих документов `parts.*.results` и `parts.*.doc`, даже если короткий итог не изменился. Источник закрепляется на новейшем коммите состояния и этих документов; дата новой записи не предшествует этому коммиту. Одинаковое содержание имеет стабильный ID; изменение времени сборки не создаёт новость. Это детерминированное чтение состояния и описаний, а не AI-пересказ и не новая научная проверка.
- Для нового графика, полноценного объяснения, нового исследования или результата, не включённого в текущее состояние, агент регистрирует источник и материал командами выше. Новый ZIP сам по себе не объясняет свой научный смысл. Сборка не угадывает его содержание. Лента сообщает о результатах, исправлениях и отрицательных выводах, не о каждом rebuild.
- Публикационный координатор обновляет общий дневник и состояние исследования один раз за сеанс. Параллельные авторы работают в отдельных материалах, чтобы не конфликтовать в общих реестрах.
- Не объявляйте расписание научных агентов существующим, если настроена только сборка сайта. GitHub Pages размещает готовый сайт; исследования выполняются отдельно.
